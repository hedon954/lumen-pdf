# 应用内检查更新并原地替换

## 问题

已安装的 LumenPDF 不会知道 GitHub 上有没有新版本。用户要自己打开发布页、下载 DMG，再把应用拖进「应用程序」。正在运行的副本也不会被替换。

## 用户行为

- 应用菜单提供「检查更新…」。设置里有「更新」页，可以检查、查看当前版本，并开关「启动时检查更新」。这个开关默认开启，改动立即生效。
- 启动时若开关开启，且距离上次成功检查已超过 6 小时，就向官方仓库查询最新稳定版。查询失败时不弹错误；15 分钟内不重复自动查询。界面测试启动参数不会触发自动查询。
- 手动检查不受上述间隔限制。已是最新版本时说明当前版本。查询失败时说明原因。
- 发现更高的稳定版时，主窗口顶部出现提示，可以查看或选择稍后。稍后只在本次运行中收起提示。手动检查会直接打开更新说明。
- 更新说明包含版本和发布说明。用户确认后才下载。下载过程中可以看到进度，也可以取消。
- 确认安装后，应用校验安装包，把新副本替换到当前 `.app` 的位置，去掉隔离属性，然后重新打开。笔记、单词、阅读进度和设置仍留在原来的位置。
- 从只读磁盘映像或系统隔离副本运行时，不替换当前副本，并把安装包放到「下载」里供手动拖入「应用程序」。当前位置不可写时也一样。
- 校验失败、安装包里的版本和发布版本不一致，或替换失败时，不留下半成品。替换失败会恢复原来的应用。
- 草稿、预发布、当前版本和更旧版本都不会安装。下载只走官方仓库的发布地址，以及 GitHub 发布资源的后续跳转。
- 使用稳定签名身份时，原地更新后钥匙串里的 API Key 仍可使用。ad-hoc 包更换二进制后，系统仍可能要求重新输入 API Key，这与重新安装相同。

## 非目标

不在用户确认前自动替换应用。不安装预发布版本，也不降级。不生成 Sparkle appcast，不做增量差分。`make upgrade` 仍只给开发者把当前构建装到 `/Applications`。

## 验收

1. 开启启动检查时，超过 6 小时后的下一次启动会查询官方发布；失败不弹窗，15 分钟内再次启动不会自动重试。
2. 有更高稳定版时出现提示。稍后只隐藏本次提示。菜单或设置里的手动检查可以再次打开说明。
3. 确认更新后，当前安装位置变成新版本，应用重新打开，原有笔记和阅读进度还在。
4. 校验失败或包内版本不符时，当前应用保持不变。
5. 从 DMG 直接运行、系统隔离运行，或目录不可写时，不替换当前副本，并在「下载」中给出安装包。
6. 草稿、预发布和更旧版本不会被当成可安装更新。
