# LumenPDF — 产品需求文档 (PRD)

## 本次迭代概述 (v1.0.9)

本次 PR 不是单一新功能，而是围绕“本机使用稳定性”和“读书笔记体验”的一轮收敛：

1. 发布链路要可信：`make dmg` 必须使用应用真实版本号，本机升级要能一条命令完成，即使 LumenPDF 正在运行。
2. 笔记页要像笔记：AI 解释保存后应按模型输出的结构展示，而不是暴露 Markdown 源码。
3. PDF 原文要可读：PDFKit 提取文本常带排版硬换行和断词，保存和展示时需要合并成自然段落。
4. AI 解释要交给模型发挥：不要用 prompt 或前端正则强行改写长度、格式和分段；同时提高输出上限，避免解释被截断。
5. 翻译气泡要减少奇怪换行：选区标题和原文展示应尽量用完整可读的段落宽度。

## 新增 / 变更功能需求

### O18 — DMG 版本号与 App 版本同步

**问题**：

打包脚本此前默认 `VERSION=1.0.0`，导致当前应用已经是 `1.0.9` 时，DMG 文件名、卷标和日志仍可能显示旧版本。发布产物版本不可信，会影响本机测试和分发判断。

**需求**：

- `make dmg` 默认从 `LumenPDF/Info.plist` 读取 `CFBundleShortVersionString` 作为公开发布版本
- `CFBundleVersion` 保留为内部 build number，不参与 DMG 文件名和普通日志展示
- DMG 文件名使用 short version，例如 `LumenPDF-1.0.9.dmg`
- 打包日志展示公开版本，例如 `1.0.9`
- 保留 `VERSION=` 环境变量覆盖能力，方便临时构建

**验收标准**：

| 用例 | 期望行为 |
| --- | --- |
| `Info.plist` 为 `1.0.9 / 9` | `make dmg` 输出 `LumenPDF-1.0.9.dmg`，日志显示 `1.0.9` |
| 手动传入 `VERSION=dev make dmg` | 产物文件名使用 `dev` |
| 修改 App 版本后再打包 | 无需改脚本，DMG 自动跟随新版本 |

---

### O19 — 本机一键升级

**问题**：

开发者本机验证新版时，需要手动打包、关闭旧应用、复制 `.app` 到 `/Applications`。如果 LumenPDF 正在运行，替换还可能失败或留下旧进程。

**需求**：

- 新增 `make upgrade`
- 执行顺序：
  1. 先执行 `make dmg`
  2. 检测当前系统是否有 `LumenPDF` 进程
  3. 如果有，先尝试普通 `kill`，超时后强制 `kill -9`
  4. 将 `build/export/LumenPDF.app` 替换到 `/Applications/LumenPDF.app`
- `/Applications` 不可写时自动使用 `sudo`
- 安装过程使用临时目录，避免复制失败时留下半成品

**验收标准**：

| 用例 | 期望行为 |
| --- | --- |
| LumenPDF 未运行 | `make upgrade` 打包后直接替换 `/Applications/LumenPDF.app` |
| LumenPDF 正在运行 | 脚本终止旧进程后替换应用 |
| `/Applications` 需要管理员权限 | 自动提示 sudo |
| 替换过程中失败 | 清理临时目录，不覆盖成坏包 |

### O20 — 笔记内容按模型输出结构展示

**问题**：

AI 解释保存到笔记后，笔记页直接用 `Text(note.note)` 展示，导致用户看到 `##`、`**`、列表标记等源码，而不是结构化阅读笔记。

**需求**：

- 笔记卡片中的用户笔记使用现有结构化文本渲染组件
- 不在前端主动重排模型输出，只做必要的换行符规范化
- 保存为 Markdown 文件时仍保留文本内容，便于外部工具继续处理
- 旧笔记无需迁移，列表展示时自动改善

**验收标准**：

| 用例 | 期望行为 |
| --- | --- |
| 笔记包含 `## 标题` | 笔记页展示为标题结构 |
| 笔记包含 `**重点**` | 笔记页展示加粗效果 |
| 笔记包含列表 | 笔记页按列表展示 |
| 模型输出普通纯文本 | 正常显示，不额外添加格式 |

---

### O21 — PDF 原文硬换行归一化

**问题**：

PDF 文本流常把视觉排版换行带进 `selection.string`，例如一句话在笔记里变成多行断裂，甚至出现 `investi-\ngating` 这类断词，影响阅读观感和搜索。

**需求**：

- 统一使用 `ContextSentenceFormatting.displayParagraph` 处理 PDF 原文：
  - 合并 CRLF / CR / LF
  - 修复英文断词换行
  - 合并连续空白为单个空格
- 新保存笔记入库前归一化 `content`
- 旧笔记展示、编辑弹窗、搜索时也按归一化文本处理
- 不改变 annotation bounds，避免影响划线 / 高亮定位

**验收标准**：

| 用例 | 期望行为 |
| --- | --- |
| 原文中有 PDF 硬换行 | 笔记卡片展示为自然段 |
| 原文中有英文断词换行 | 展示时拼回完整单词 |
| 按自然句子搜索旧笔记 | 能匹配到原先含硬换行的笔记 |
| 删除 / 跳转笔记 | 不受文本归一化影响 |

---

### O22 — 解释输出不被人为压缩或重排

**问题**：

选区解释的默认 prompt 里包含“short / concise / 不要 shorten / compact reader bubble”等长度和格式导向；前端 Markdown renderer 也用大量正则尝试“修复”模型输出。这会造成两类问题：

- 模型被提示词暗示控制长度，输出容易被限制
- 前端主动插入换行或改写 Markdown，可能破坏模型本身已经生成好的结构

**需求**：

- 解释 prompt 不再要求“长”“短”“简洁”“详细”或固定 Markdown 结构
- System prompt 只要求返回解释文本，不返回 JSON
- 旧默认 prompt 自动迁移到新默认 prompt
- 前端不再用正则重排解释内容，仅规范 CRLF / CR
- Chat request 显式设置更大的 `max_tokens`
- LLM HTTP 总超时提高，避免长解释流式生成时被过早截断

**验收标准**：

| 用例 | 期望行为 |
| --- | --- |
| 解释较长 | 请求不会因默认 token 上限过低而提前截断 |
| 模型输出 Markdown | 前端直接交给 renderer，不额外插入标题或列表换行 |
| 模型输出纯文本 | 直接展示纯文本 |
| 用户保留旧默认 prompt | 打开设置页后迁移到新默认 prompt |

---

### O23 — 翻译气泡顶部选区标题更自然换行

**问题**：

选区解释模式下，气泡顶部标题区域会因为右侧按钮和宽度竞争产生奇怪换行，长选区看起来像被强行窄列排版。

**需求**：

- 顶部选区文本归一化为自然段
- 选区文本区域优先占用可用宽度
- 允许多行自然换行，不人为截断

**验收标准**：

| 用例 | 期望行为 |
| --- | --- |
| 选中一整段英文 | 气泡顶部按可用宽度自然换行 |
| 文本来自 PDF 多行选择 | 顶部展示合并后的自然段 |
| 右上角按钮存在 | 不明显挤压标题成窄列 |

## 兼容性与回归

- **数据库**：不引入 schema 变更。笔记原文的新保存路径会归一化内容；旧数据在展示和搜索时兼容。
- **导出**：Markdown 导出仍使用已有 Rust 导出逻辑，本期不改变导出格式。
- **设置迁移**：仅当用户当前 prompt 等于旧默认值时自动替换；用户自定义 prompt 不被覆盖。
- **发布链路**：`make upgrade` 依赖 `make dmg` 产出的 `build/export/LumenPDF.app`，不会从 DMG 反向挂载安装。
- **LLM 兼容性**：`max_tokens` 使用 OpenAI-compatible chat completions 字段；若某些网关不支持该字段，错误会按现有 LLM 错误路径暴露。

## 不在本期范围内

- 对历史数据库里的 `notes.content` 做批量迁移
- 为用户暴露可配置 `max_tokens`
- 自动启动升级后的 LumenPDF
- 对模型输出内容做前端二次摘要、改写或纠错
- 改动整句翻译的长难句 breakdown 规则
