# 选区就是要翻译的那段文字

## 技术结论

上一次语境修复用三件互不相干的东西决定「这句话是什么」：选区包围盒的中心、`PDFView.currentPage`，以及「句子太短或从选中词开头就再并一句」。选区本身才是一段按阅读顺序排列的字符。句子是这段字符碰到的 `NLTokenizer` 句子，补到句界为止。滚动改变的是这段字符在屏幕上的位置，不是这段字符还在不在。

## 模块边界

| 模块 | 职责 |
| --- | --- |
| `ReadingLine` / `ReadingSentenceContext` | 纯函数。输入是带页码的视觉行，以及每行里被选中的字符区间。输出是选中的词和覆盖这些字符的句子。 |
| `ParagraphJoiner` | 判断相邻两行是不是同一段，包括跨页的那一对。 |
| `PDFSelectionMarkupGeometry` | 用 `PDFSelection` 的逐页字符区间取出选中行，并带上前后页未选中的正文行，供补全句界。 |
| `PDFReadingSelection` | 拖选跨页而 `PDFSelection` 丢掉起始页时，用按下和松开的页内坐标重做选区。 |
| `SelectionTrackingPDFView` | 在 `super` 发出选区通知之前记下拖选的两个点。 |
| `ReadingPopoverModel.moveAnchor` | 只更新浮窗锚点，不换一次翻译，也不重置浮窗。 |

SwiftUI 视图仍不调用 `BridgeService`。高亮、笔记和语法树的存储格式不变。

## 关键规则

PDF 里没有句子。顺序固定为：先确定选中了哪些字符，再把软换行拼回段落，最后才用系统句子边界切开。

一行被选中，是因为它的字符区间落在选区里，不是因为它和选区包围盒相交的面积最大。`currentPage` 不参与这个判断。页面滚到两页中间时，当前页经常还是前面那一页，用它来选句就会拿成前面那句。

段落拼接仍看行框。同一页里，短的句首行可以接上后面的正文。跨页时没有共同的行距：上一页最后一行要像还没写完的正文（写满，或行末连字符接小写），才和下一页第一行算同一段。拼好之后，`NLTokenizer` 给出句子区间，取和选中字符相交的那些句，从第一句的句首到最后一句的句末。不相交的邻句不加入。`Mr.` 和数字加点的合并还在。按 `.!?` 手切、以及「句子过短或从选中词开头就带上前后句」，都不再使用。

半个词先补成它所在的词。选区里已经有多个词时，送去句子翻译的是补全后的句子，页面上的临时标牌仍只画用户拖过的行框。

跨页成员以 `numberOfTextRanges(on:)` 和 `range(at:on:)` 为准。`pages`、`string` 和 `selectionsByLine()` 会丢掉拖选的第一页，不能用来决定这一页有没有被选中。字符区间存在时，行框从 `page.selection(for: range)` 来。区间也没有、但按下和松开落在不同页时，用这两个点在各页上重建选区：起始页从按下处到该页正文末，中间页取正文，结束页从正文首到松开处。只为包围盒非空就把邻页算进选区的做法会把前面一页的句子当成选区，这条路径删掉。

滚动和缩放不再关闭翻译。`PDFView` 的裁剪区域变化时，用当前还能看见的选区行框换算屏幕矩形，调用 `moveAnchor`。一行都看不见时才退回整段选区的矩形。浮窗的 generation 不变，所以进行中的翻译不重来。用户拖动过浮窗之后，面板自己留在拖开的位置。

## 测试与运行时验收

- `ReadingSentenceContext`：选中一整句不含前一句；后面那句不会被前面那句替换；半句补全时不带走下一句；句首词、`Mr.`、连字符、分栏、跨页顺序、跨页续句不含上一句。
- `PDFReadingSelection`：报告的选区只有第二页时，用跨页拖选坐标重建，第一页的文字仍在，并且排在前面。
- 双指滚动时浮窗跟着选区、不消失，需要在运行中的应用里看。上述测试不能代替这次手势验收。
