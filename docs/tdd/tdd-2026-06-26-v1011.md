## 本次迭代技术方案

对应 PRD：`docs/prd/prd-2026-06-26-v1011.md`（O24 / O25 / O26 / O27 / O28 / O29）。

本次 PR 覆盖五条技术线：

1. 选区解释：Swift UI 先收集用户疑问，再把 `focus` 传给 Rust LLM prompt。
2. 气泡布局：解释气泡使用主窗口尺寸计算宽高上限，长内容内部滚动。
3. 设置页：按语言族加载 / 保存 prompt，并在目标语言变化时热更新运行时配置。
4. 缓存隔离：Rust domain/application/infrastructure 全链路按 `target_language` 读写翻译缓存。
5. 桌面体验：主窗口 frame 持久化。

## O24 — 先提问再解释

### Swift 交互状态

`PDFReaderView` 中，选区菜单点击「解释」后调用 `presentExplanationPrompt`，构造 `TranslationBubbleRequest`：

- `result = nil`
- `isTranslating = false`
- `isExplanationMode = true`

这让 `TranslationBubble` 进入解释前状态，只展示输入栏和原文，不触发网络请求。

### 提交流程

`TranslationBubble` 暴露：

```swift
let onAskExplanation: (String) -> Void
```

用户点击按钮后：

1. 对输入做 `trimmingCharacters(in: .whitespacesAndNewlines)`。
2. 空字符串表示通用解释。
3. 非空字符串作为 `focus`。
4. 回调 `PDFReaderView.requestExplanation(..., focus:)`。

### Bridge / Rust API

Swift bridge：

```swift
func explainSelectionStreaming(selection: String, context: String, focus: String, onPartial: ...)
```

Rust UniFFI：

```rust
pub async fn explain_selection_streaming(
    selection: String,
    context: String,
    focus: String,
    callback: Arc<dyn TranslationStreamCallback>,
)
```

`focus` 只影响解释 prompt，不影响翻译缓存。

## O25 — 解释气泡尺寸比例和滚动

### 可用尺寸来源

`PDFReaderView` 在气泡外层包一层 `GeometryReader`，把 `bubbleProxy.size` 传给 `TranslationBubble.availableSize`。

### 宽高策略

`TranslationBubble` 内部计算：

- `effectiveAvailableSize`：为极小窗口提供最小计算基准。
- `cardWidth`：解释模式按窗口宽度比例限制。
- `maximumAutomaticCardHeight`：解释模式按窗口高度比例限制整张卡片。
- `maximumAutomaticContentHeight`：扣除 header / divider / padding 后的可滚动内容高度。

### 滚动策略

解释模式下，结果内容和解释前 prompt 内容都放入 `ScrollView`：

- 自动高度使用 `maximumAutomaticContentHeight`。
- 用户手动 resize 后，内容区域使用剩余空间。
- 长解释和长原文不再撑高整张气泡。

## O26 / O27 — 多语言 prompt 与运行时配置同步

### 语言族映射

`PromptTemplateDefaults.storageSuffix(for:)` 将语言映射为：

- `zh`：包含 `中文` 或 `Chinese` 的目标语言。
- `en`：其他目标语言。

当前内置两套 `LanguageDefaults`：

- `chinese`
- `english`

### 持久化 key

每个 prompt 字段按语言族派生 key：

```swift
"word_prompt_template_zh"
"word_prompt_template_en"
"sentence_prompt_template_zh"
"sentence_prompt_template_en"
...
```

切换语言时：

1. `persistPromptTemplates(for: loadedPromptLanguage)` 保存旧语言。
2. `loadPromptTemplates(for: newLanguage, replacingLegacyDefaults: false)` 加载新语言。
3. `loadedPromptLanguage = newLanguage`。
4. `syncRuntimeConfig()` 立即热更新 Rust LLM 配置。

### Stale 内置模板修复

早期实现可能把中文内置模板写入 English 槽位。加载时如果发现 stored value 属于内置模板集合，但不属于当前语言内置模板集合，则视为 stale，替换为当前语言默认值。

### Runtime config 同步

`syncRuntimeConfig()` 统一负责：

- 保存当前语言 prompt；
- 调用 `BridgeService.shared.updateConfig(...)`；
- 传递 base URL、API key、model、target language、user prompts、system prompts。

因此目标语言切换后，下一次 API 调用不依赖用户再点「保存设置」。

## O28 — 翻译缓存按目标语言隔离

### Domain trait

`TranslationCacheRepository` 从：

```rust
get(word, sentence_hash)
set(word, sentence_hash, result)
```

扩展为：

```rust
get(word, sentence_hash, target_language)
set(word, sentence_hash, target_language, result)
```

### Domain service

`TranslationDomainService` 新增：

```rust
cache_target_language: String
```

并提供链式配置：

```rust
with_cache_target_language(target_language)
```

普通翻译和 streaming 翻译的 cache hit / cache write 都传入该字段。

### Application / interfaces 注入

`TranslationUseCase` 保留旧构造函数，同时新增：

```rust
new_for_language(..., target_language)
with_phonetic_for_language(..., target_language)
```

`interfaces/api.rs` 在每次翻译请求开始时读取最新 `llm_config()`，并用 `config.target_language.clone()` 构造 use case。这保证热更新后的语言能进入 cache key。

### SQLite schema

新表定义：

```sql
CREATE TABLE IF NOT EXISTS translation_cache (
    id              TEXT PRIMARY KEY,
    word            TEXT NOT NULL,
    sentence_hash   TEXT NOT NULL,
    target_language TEXT NOT NULL DEFAULT '',
    response_json   TEXT NOT NULL,
    source          TEXT NOT NULL DEFAULT 'llm',
    created_at      INTEGER NOT NULL,
    hit_count       INTEGER NOT NULL DEFAULT 0,
    UNIQUE(word, sentence_hash, target_language)
);
```

### 旧库迁移

`migrate_translation_cache_language_key`：

1. 用 `PRAGMA table_info(translation_cache)` 判断是否已有 `target_language`。
2. 若没有，重命名旧表为 `translation_cache_old`。
3. 创建新表和三列唯一键。
4. 把旧数据插入新表，`target_language` 使用默认空字符串。
5. 删除旧表。

该方案可以移除旧的 `UNIQUE(word, sentence_hash)`，否则 SQLite 无法为同一词句保存多语言缓存。

### 测试

新增 domain unit test：

- English service 翻译 `run + sentence`，写入 English cache。
- Chinese service 翻译同一 `run + sentence`，不能命中 English cache，写入中文 cache。
- 最终断言两个目标语言 cache entry 同时存在。

## O29 — 主窗口 frame 持久化

### 技术方案

`WindowFramePersistence` 使用 `NSViewRepresentable` 获得宿主 `NSWindow`：

- 启动时从 `UserDefaults` 读取保存的 frame。
- 调用 `window.setFrameAutosaveName(...)` 使用 macOS 原生 autosave。
- 监听 close / move / resize end 等通知并手动保存 frame。

### 约束

- 只影响主窗口，不改变 PDF 阅读位置保存逻辑。
- 保存的是窗口 frame，不是 PDF 页码或缩放状态。

## 回归风险与处理

| 风险 | 处理 |
| --- | --- |
| 用户切换语言后 prompt 未同步到 Rust | `onChange(targetLanguage)` 调用 `syncRuntimeConfig()` |
| 英文缓存污染中文结果 | cache key 增加 `target_language` |
| 旧数据库唯一键阻止多语言缓存 | 迁移时重建 `translation_cache` 表 |
| 用户自定义 prompt 被覆盖 | 仅替换内置默认值 / stale 内置值，按语言族保存自定义值 |
| 长解释撑开窗口 | 解释内容和 prompt 预览统一使用受限 `ScrollView` |

## 验证建议

1. 设置目标语言为 English，翻译一个词，确认结果为英文。
2. 不点击保存，直接切换目标语言为简体中文，再翻译同一词同一句，确认结果为中文且不会命中 English 缓存。
3. 切回 English，再翻译同一词同一句，确认可命中 English 缓存。
4. 点击「解释」，确认先显示输入框；输入问题后按钮显示「解释」并围绕问题输出。
5. 生成较长解释，确认气泡高度受限且内容可滚动。
6. 调整主窗口大小和位置，重启后确认恢复。
