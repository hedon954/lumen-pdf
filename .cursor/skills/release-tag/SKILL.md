# LumenPDF 版本收尾

## 目标

用 AI 手写维护发布记录，不再依赖 git-cliff 的流水线输出。每次发布都要做到：版本号明确、`CHANGELOG.md` 可读、每条具体变更都有 commit URL、release workflow 只负责打包和发布，不再生成或提交 changelog。

## 基本规则

- 在 LumenPDF 仓库根目录执行。
- Commit message 保持 `type(scope):` 前缀为英文，冒号后的描述用中文。
- 不使用 git-cliff；新的 changelog 段落不要加入 `generated by git-cliff` 注释。
- 不覆盖用户未说明的改动。工作区脏时，先确认哪些文件属于当前任务。
- `CFBundleShortVersionString` 是公开版本号，`CFBundleVersion` 是内部 build number。普通 `1.0.N` 发布默认 build number 为 `N`，除非用户另有要求。
- Release note 不是 commit 流水账，但每条具体变更都必须带至少一个 GitHub commit URL。
- Annotated tag message 必须与当前版本 changelog 对齐：标题写版本号，正文提炼版本段落开头的发布摘要，并指向 `CHANGELOG.md` 获取完整变更。禁止只写 `LumenPDF vX.Y.Z`。

## 工作流

### 1. 同步和确认版本边界

```bash
git fetch origin --tags
git status --short --branch
git tag --sort=-version:refname | sed -n '1,10p'
plutil -p LumenPDF/Info.plist | rg 'CFBundleShortVersionString|CFBundleVersion'
```

- 确认 `VERSION`、`TAG=v$VERSION`、`PREVIOUS_TAG`。
- 默认用最新 semver tag 作为 `PREVIOUS_TAG`，除非用户指定基线。
- 如果目标 tag 已存在，先停止并确认用户是要检查、替换，还是发布另一个版本。

### 2. 收集变更证据

```bash
git log --reverse --format='%H%x09%s%x09%an' "${PREVIOUS_TAG}..HEAD"
git diff --stat "${PREVIOUS_TAG}..HEAD"
git remote get-url origin
```

Commit URL 使用：

```text
https://github.com/hedon954/lumen-pdf/commit/<full-sha>
```

面向用户的 changelog 中，通常跳过 merge commit 和旧的自动 changelog commit，除非它们本身就是这次发布要说明的对象。

### 3. 更新版本号

```bash
/usr/libexec/PlistBuddy -c "Set :CFBundleShortVersionString ${VERSION}" LumenPDF/Info.plist
/usr/libexec/PlistBuddy -c "Set :CFBundleVersion ${BUILD}" LumenPDF/Info.plist
```

### 4. 重写 CHANGELOG.md

- 新版本段落放在 `# Changelog` 下方。
- 标题保留 compare URL。
- 正文用中文；Swift、Rust、PDFKit、UniFFI、DMG、API、LLM、Keychain 等产品或技术名保留原文。
- 优先使用面向读者的分组，例如 `主要变化`、`修复`、`工程与发布`；没有内容的分组不要写。
- 每条具体变更都在句尾附 commit URL。

推荐结构：

```markdown
---

## [1.0.15](https://github.com/hedon954/lumen-pdf/compare/v1.0.14..v1.0.15) - 2026-07-04

这一版聚焦于……

### 主要变化

- 优化……（[abc1234](https://github.com/hedon954/lumen-pdf/commit/<full-sha>)）

### 修复

- 修复……（[def5678](https://github.com/hedon954/lumen-pdf/commit/<full-sha>)）
```

### 5. 验证

- 总是运行 `git diff --check`。
- Rust、UniFFI、DB 或发布关键路径有变更时，运行 `cd lumen-pdf-core && cargo test`。
- 发布前如果时间允许，运行 `make dmg` 或当前 macOS build 命令。
- 确认 release workflow 不再包含 git-cliff，也不会自动提交 `CHANGELOG.md`。

### 6. 提交、打 tag、推送

用户要求发布时执行：

```bash
git add LumenPDF/Info.plist CHANGELOG.md .github/workflows/release.yml CLAUDE.md
git commit -m "chore(release): 发布 v${VERSION}" -m "整理 v${VERSION} 发布记录并同步版本信息。\n\n验证：说明实际执行的发布检查。"
git push origin main
git tag -a "v${VERSION}" \
  -m "LumenPDF v${VERSION}" \
  -m "${TAG_SUMMARY}" \
  -m "完整变更见 CHANGELOG.md。"
git push origin "v${VERSION}"
```

`TAG_SUMMARY` 必须根据 `CHANGELOG.md` 当前版本标题后的首段摘要填写，保持简洁、面向用户，不复制完整条目列表。创建 tag 后使用 `git tag -n99 "v${VERSION}"` 复核标题和正文，再推送。

实际 staging 文件以本次改动为准，不要 stage 无关用户改动。

### 7. 最终汇报

说明版本号、build number、changelog 状态、commit hash、tag、推送结果，以及跑过哪些检查。若已触发 GitHub Release workflow，说明它会读取 `CHANGELOG.md` 中匹配版本段落作为 release body。
